# Isoform rework plan (draft for Bo, 2026-11-14)

## Why

Last 30 days on `feat/iphone-companion`: 1,587 merges (about 53 a day), 1,584 fix commits, 123 fixes for things that broke again or still did not work, 15 reverts. The desktop Go code is 668,000 lines in 2,275 files, almost all in one package; the screens are 136,000 lines. Fixes cluster in Today, the brief, the iPhone app and chat (one Today component took 79 fixes).

The bugs come from three things, not from Wails:

1. Too much app, too tangled: one package holds every feature, so a change in one quietly breaks another.
2. Too fast: about 53 merges a day, mostly on focused tests, with several sessions editing the same files.
3. Nothing tests the real app: tests check pieces; Bo finds the regressions.

Switching frameworks would rewrite about 800,000 lines and keep all three causes. We keep Wails and revisit after step 2 (see "Framework" below).

## 1. Shrink to a core

Keep (the product):

| Area | What stays |
|---|---|
| Capture | Screen and activity capture, privacy controls, Closed Eyes |
| Today and the brief | Morning and evening brief with audio, Your week |
| Chat | Main chat on the computer and the phone, Tasks run from chat |
| You | About you, How you do things, Who you know |
| Activity | Your day and the screen timeline |
| Phone | Brief, chat and connection (relay plus direct path) |
| Basics | Onboarding, Settings, menu bar, updates |

Turn off (behind a switch, code kept, can come back one at a time once the core is solid):

| Feature | Why off |
|---|---|
| Automations and cron prompts | Rarely used, many background paths |
| Playbooks, SOPs, deliverables, goals | Not in the core flow |
| Proactive voice cards in chat | Slow and privacy-heavy (last night's chat regressions) |
| Calendar holds | Many queue and relay edge cases |

Delete: the shadow agent and Agency code (the worklog file alone had 178 fix touches), code with no caller once the features above are off, old feature switches that are always on, and duplicate paths kept "for fallback" that never run.

Also kept (Bo, Nov 14): the quick-chat spotlight window, Agent of You, and the Apple Watch app (it gathers data).

Changed (Bo, Nov 14):

- Computer use: drop our own driver (cua) and opencli browser tasks; hand that work to agents that already do it (Claude Code with Claude in Chrome for the web, Claude or OpenAI computer use for desktop apps). Isoform keeps the decision and the data and passes down only the task; every approved or rejected task is feedback.
- Topics: both projects and subjects followed. Each topic carries Isoform's proposed next piece of work with yes, no and "not mine", on the computer and the phone; a yes runs the work through Claude Code. Built once a day as a saved copy (no live registry), filtered only by the user's own choices (forget, excluded apps, Closed Eyes) at build time; anything that leaves the computer (an agent task, the phone) passes the same filter. Design first.

## Guiding principle

Gather as much signal as we can, turn it into work people judge, and treat their judgments as the most valuable data we have (Bo, Nov 14). Every product decision is shaped toward this.

- Scope: each person's own data first, on their own devices, improving their own Isoform; learning across users comes later, as an explicit decision.
- Measured daily in the morning report: proposals made, answered and accepted; brief items acted on. If these rise, the thesis works; more capture alone does not.
- Proactive work starts where the hit rate is high: follow-ups people asked for, meeting prep, drafts of things already started.
- Trust grows the data: data stays local, is visible and deletable, and Closed Eyes always wins.

## 2. Split the core into modules

Follow the brief's pattern (`internal/brief`, the most stable piece this week). Each module has one owner session, a small public interface, and its own tests:

- `internal/capture`: screen, activity, privacy gates
- `internal/brief`: already split
- `internal/today`: page snapshot for Today and Your week
- `internal/chat`: main chat, turns, Tasks
- `internal/memory`: memory, know-how, people, About you snapshots
- `internal/mobile`: phone protocol, relay, direct path
- `internal/privacy`: one place for withdrawal, forget, Closed Eyes and the stamps every saved copy checks

Order: privacy first (every other module depends on it), then chat and mobile (most regressions), then today and memory. Each move is a pure refactor with the full suite green before and after.

## 3. Merge gate

- A merge queue on the Mac mini tests the combined result, the way large teams do (Google presubmit, Uber SubmitQueue, GitHub merge queue): each PR is tested on top of everything queued before it, and lands only if that combination passes.
- A merge needs: the full Go suite for the touched module plus its dependents, the frontend suite, and the daily real-app check passing on the tip it lands on.
- About 10 merges a day. Fixes for what Bo sees first; features wait.
- Several sessions may edit the same files (git merges them); each module has an owner who reviews changes to it.
- A regression gets a revert within the hour, then a fix with a guard test.

## 4. A real test every day

Two runs, every morning before Bo's day starts:

1. Real app on test data (Mac mini): build the app with the release script, launch it on a test data folder seeded with a scripted day, and drive it through every core page (Today, brief with audio, chat send and answer, Tasks, You pages, Activity, Settings, the phone pairing and brief through a local relay). Each page must paint within its time budget and match its screenshot. Failures open a fix task before anything else merges.
2. Bo's real day replay (MacBook, read-only): replay yesterday through the brief and the page snapshots, compare with the day before (counts, timings and errors only, never content), and flag anything that got worse.

The results go in the morning report.

## 5. Framework

After step 2, try a small native Mac app (SwiftUI) that shares its client code with the iPhone app and talks to the Go core over a local socket. Switch only if it clearly wins on bugs and speed. Until then, Wails stays.
